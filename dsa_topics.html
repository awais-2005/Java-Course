Arrays & Strings

The raw material almost every other topic is built on top of.

An array is a block of memory holding elements at contiguous, indexable positions; a string is just an array of characters with a few extra conventions. Nearly every technique in this guide — Two Pointers, Sliding Window, Binary Search, Dynamic Programming — is expressed *on top of* an array. Getting fluent with array mechanics first means every later topic reads as a variation on a theme instead of a brand new language.

Indexing & contiguous memory

Because array elements sit next to each other in memory, reading or writing at any index is O(1). This is the single fact that makes arrays the default container: you trade flexibility (fixed size, expensive insert/delete in the middle) for raw speed of access. Compare this to a Linked List, where access is O(n) but insertion is O(1) once you're at the right node — the two structures are near-opposites.

Static vs. dynamic arrays

A static array (like a C array or Java's `int[]`) has a fixed capacity set at creation. A dynamic array (Python's `list`, Java's `ArrayList`, C++'s `vector`) grows by allocating a new, larger block and copying elements over when it runs out of room — usually doubling in size, which gives amortized O(1) append even though any single append can occasionally cost O(n).

Prefix sums

Precomputing `prefix[i] = arr[0] + arr[1] + ... + arr[i-1]` lets you answer 'sum of any subarray' in O(1) after O(n) preprocessing, instead of O(n) per query. This single trick underlies a huge share of 'range sum' and 'subarray equals target' problems, and it pairs naturally with Hashing when you need to count how many prefix sums have been seen before (see Subarray Sum Equals K).

In-place manipulation

Many array problems ask you to modify the array without allocating extra space — reversing, rotating, removing duplicates, or partitioning by some condition. The common pattern is to use one or more index pointers that read and write into the same array, which is the seed idea that grows into the full Two Pointers technique.

Kadane's algorithm

Kadane's is the canonical 'maximum subarray sum' technique: walk the array once, keeping a running sum that resets to 0 whenever it goes negative, and track the best value seen. It's a tiny example of greedy, local decision-making standing in for what looks like it should need brute force — a preview of the intuition behind Greedy algorithms and 1-D Dynamic Programming.

String-specific concerns

Strings add their own wrinkles: immutability in languages like Python and Java (every concatenation can create a new string, so building with a list/`StringBuilder` and joining once matters for performance), character encoding, and pattern matching. Two-pointer palindrome checks, sliding-window substring problems, and trie-based prefix search (see Tries) are all string problems wearing an array's clothes.

Hashing

Trading memory for near-instant lookup.

A hash map (or hash set) uses a hash function to convert a key into an index into a backing array, giving average O(1) insert, delete, and lookup. Hashing is arguably the single highest-leverage topic on this list: an enormous fraction of 'brute force O(n²) → optimized O(n)' upgrades on LeetCode come from replacing a nested loop with a hash map that remembers what you've already seen.

How a hash map works

A hash function maps a key to an integer; that integer, modulo the table size, picks a 'bucket' in an underlying array. A good hash function spreads keys uniformly so buckets stay small, keeping operations close to O(1) on average — the worst case is still O(n) if everything collides.

Collision handling

Two common strategies: chaining, where each bucket holds a small list of entries that share it, and open addressing, where a colliding key probes forward to the next free slot. You rarely implement this yourself on LeetCode, but understanding it explains *why* worst-case hash map operations degrade to O(n) and why table resizing exists.

Hash sets vs. hash maps

A hash set only tracks membership ('have I seen this value before?'); a hash map associates a value with each key. Reach for a set when you just need existence checks (duplicates, visited nodes), and a map when you need to remember a count, index, or other payload alongside the key.

Frequency counting

Counting how many times each element appears is probably the single most common hashing pattern — anagrams, majority elements, top-k frequent items (paired with a Heap), and sliding-window character counts (paired with Sliding Window) all start by building a frequency map.

Hashing complex keys

You can hash more than single integers: tuples, sorted strings (for anagram grouping), frozensets, or serialized paths through a Tree or Graph (for memoizing recursive state, tying directly into Dynamic Programming memoization). The key just needs to be immutable and to hash equal values identically.

Prefix-sum + hash map combo

A very common 'medium' pattern: as you scan an array building a running prefix sum, store each prefix sum's count (or first index) in a hash map. Then 'is there a subarray summing to k?' becomes 'have I seen prefix_sum - k before?' — turning an O(n²) subarray scan into O(n).

Two Pointers

Two indices walking through data so you don't have to check every pair.

The two-pointer technique replaces a nested loop (checking every pair of elements, O(n²)) with two indices that move through the data in a single coordinated O(n) pass. It works whenever moving one pointer lets you safely conclude something about a whole range of possibilities at once — most often because the underlying array is sorted or has a monotonic property.

Opposite-direction pointers

One pointer starts at the left, one at the right, and they move toward each other. This is the classic shape for 'find a pair that sums to X' on a sorted array, palindrome checks, and container/area problems like Container With Most Water — at each step you can prove that moving the *worse* pointer inward is always at least as good as any other move.

Same-direction pointers

Both pointers start at the left and move rightward, with one (often called 'slow') lagging behind the other ('fast'). This shape shows up in 'remove duplicates in place', partitioning arrays around a pivot (as in quicksort's partition step, see Sorting), and merging two sorted structures.

Fast & slow pointers (Floyd's cycle detection)

A special same-direction variant where the fast pointer moves two steps for every one step of the slow pointer. If there's a cycle, they're guaranteed to meet; if there isn't, the fast pointer reaches the end first. This is the standard way to detect cycles and find the middle of a Linked List in O(1) space.

Three pointers / partitioning

Some problems need three regions maintained simultaneously — for example, the Dutch National Flag problem (Sort Colors) uses a low, mid, and high pointer to partition an array into three groups in a single O(n) pass with O(1) extra space, instead of a full sort.

When two pointers doesn't apply

The technique fundamentally relies on being able to discard a whole range of candidates at once. If the array is unsorted and order matters, or elements need to be compared non-locally, two pointers usually won't work directly — you'd sort first (paying an O(n log n) cost) or reach for Hashing instead.

Sliding Window

A two-pointer window that grows and shrinks over a contiguous range.

Sliding window is a specialization of Two Pointers for problems about *contiguous* subarrays or substrings — 'longest/shortest/count of substrings satisfying some condition.' Instead of recomputing a property from scratch for every possible window (O(n²) or worse), you maintain the property incrementally as a `left` and `right` boundary slide across the data, giving O(n) total work.

Fixed-size windows

When the window length k is given up front, you compute the property for the first k elements, then slide by one: add the incoming element, remove the outgoing one, and update in O(1). Maximum Average Subarray I is the simplest possible example of this shape.

Variable-size windows

Most sliding-window problems don't fix the size — instead you grow `right` until the window violates some constraint, then shrink from `left` until it's valid again, tracking the best window seen. This 'grow, then shrink' rhythm is the real signature of the technique, and it's what makes Minimum Window Substring and Longest Substring Without Repeating Characters feel different from a fixed-size problem.

Window state via hashing

The window's 'state' — character counts, distinct-element counts, sum — is almost always tracked with a hash map or a fixed-size array (when the alphabet is small, like lowercase letters). Updating that state as the window slides is what keeps each step O(1) amortized rather than O(k).

Monotonic deque windows

When you need the *max or min* inside a sliding window rather than a sum or count, a plain running value doesn't work because the max can leave the window. Sliding Window Maximum solves this with a monotonic deque — see Monotonic Stack/Queue for the full mechanics.

Recognizing the pattern

Look for the phrase 'contiguous subarray/substring' combined with 'longest', 'shortest', 'count of', or 'contains at most/exactly k distinct'. If the subarray doesn't need to be contiguous, sliding window is usually the wrong tool — you likely want Dynamic Programming or Backtracking instead.

Sorting

Ordering data — and the algorithm family that teaches divide-and-conquer.

Sorting rearranges elements into order, and it's rarely the whole problem on LeetCode — it's usually the *setup* that makes a harder technique possible: sorted data unlocks Binary Search and Two Pointers, and the sorting algorithms themselves are the cleanest introduction to Divide and Conquer.

Comparison sorts: bubble, insertion, selection

These O(n²) algorithms repeatedly compare and swap adjacent or nearby elements. They're rarely fast enough to be the final answer, but insertion sort specifically is worth knowing because it's efficient on nearly-sorted data and is what many real standard libraries fall back to for small subarrays.

Merge sort

Merge sort splits the array in half, recursively sorts each half, then merges the two sorted halves in O(n). This is the textbook Divide and Conquer algorithm — the merge step is also directly reusable for problems like counting inversions (Count of Smaller Numbers After Self, Reverse Pairs).

Quick sort & quickselect

Quick sort picks a pivot, partitions the array so smaller elements are left of the pivot and larger are right (using the same two-pointer partition idea), then recurses on each side. Its close cousin, quickselect, only recurses into the side that contains the k-th element you care about, giving average O(n) for problems like Kth Largest Element in an Array.

Non-comparison sorts: counting, radix, bucket

When keys are integers in a known, small range, you can sort in O(n + k) by counting occurrences directly rather than comparing elements — this is the theoretical floor-breaker that gets around the O(n log n) comparison-sort lower bound. Radix sort extends this by sorting digit-by-digit; bucket sort spreads elements into buckets by value range and sorts each bucket separately.

Custom comparators

A large share of 'sorting' interview problems are really about *designing the right comparator* — e.g., sorting numbers as strings so their concatenation is largest (Largest Number), or sorting by a derived rule instead of natural order (Custom Sort String, H-Index). The sorting algorithm underneath is a solved problem; the comparator is the puzzle.

Binary Search

Halving the search space every step — not just for sorted arrays.

Binary search finds a target in O(log n) by repeatedly halving a search space, but the deeper idea is more general than 'search a sorted array': it works on *any monotonic condition* — any situation where the answer to 'is X good enough?' flips from false to true (or true to false) exactly once as X increases. Recognizing that shape is what separates people who can only binary-search an array from people who can binary-search an answer.

Classic search on a sorted array

Maintain `lo` and `hi` bounds, check the midpoint, and discard half the array based on the comparison. The classic bug is off-by-one errors in the loop condition and midpoint update — always be explicit about whether bounds are inclusive or exclusive and stay consistent.

Lower bound / upper bound

Instead of 'does the target exist', many problems want 'the first index where value >= target' (lower bound) or 'the first index where value > target' (upper bound). This variant is what powers Find First and Last Position of Element in Sorted Array and is the building block for order-statistics queries in a Fenwick Tree.

Binary search on a rotated sorted array

A rotated sorted array is still 'half sorted' at every midpoint — one half is guaranteed to be properly ordered, so you can always determine which half to keep searching. Search in Rotated Sorted Array and Find Minimum in Rotated Sorted Array are the two canonical drills for this.

Binary search on the answer

For optimization problems ('minimize the maximum', 'find the smallest capacity that works'), define a predicate `feasible(x)` that's monotonic, then binary search over the *range of possible answers* rather than over the input array. Koko Eating Bananas and Capacity To Ship Packages Within D Days are the textbook introductions to this pattern, which later reappears in Shortest Path problems solved by binary search + BFS.

Binary search on 2D structures

A matrix that's sorted row-by-row and column-by-column can be searched by treating it as a flattened 1D array (Search a 2D Matrix) or by starting from a corner and eliminating a row or column at each step, depending on exactly how it's sorted.

Recursion

A function calling itself on a smaller version of the same problem.

Recursion is a function solving a problem by calling itself on a smaller subproblem, until it reaches a base case simple enough to answer directly. It's less a 'topic' than a way of thinking that underlies Backtracking, tree/graph DFS, Divide and Conquer, and top-down Dynamic Programming — getting comfortable with it early pays off everywhere else.

Base case & recursive case

Every correct recursive function needs a base case (the smallest input, answered directly, no further recursive call) and a recursive case that reduces the problem toward that base case. Forgetting the base case — or writing a recursive case that doesn't actually shrink the problem — is the single most common source of infinite recursion / stack overflow bugs.

The recursion tree & call stack

Each recursive call pushes a new frame onto the call stack, and that stack of pending calls forms a tree if you draw out every branch. Thinking in terms of this tree explains time complexity (count the nodes) and space complexity (the deepest path is the max stack depth) far more intuitively than trying to trace the code line by line.

Tail recursion & why it (mostly) doesn't help in Python

A tail-recursive call is one where the recursive call is the very last operation, with nothing left to do after it returns — in languages that optimize this ('tail call optimization'), it can run in O(1) stack space. Python and Java do *not* perform this optimization, so deep tail recursion in those languages can still overflow the stack; an iterative loop is the safe rewrite.

Memoization

When a recursive function is called repeatedly with the same arguments (common in problems phrased recursively, like Fibonacci or counting paths), caching results by input avoids redundant work. This is exactly top-down Dynamic Programming — memoized recursion and DP are the same idea described two different ways.

Recursion vs. backtracking

Plain recursion computes and returns a single answer for each call. Backtracking adds the extra idea of *undoing* a choice after exploring it, so the same shared state can be reused across many branches of the tree — that's the difference between 'recursively compute a value' and 'recursively explore all possibilities'.

Linked Lists

A chain of nodes — cheap to splice, expensive to search.

A linked list stores elements as nodes, each pointing to the next (and, in a doubly linked list, the previous). It's the structural opposite of an array: O(1) insertion/deletion once you're at the right node, but O(n) to reach that node in the first place, since there's no random access.

Singly vs. doubly linked lists

A singly linked list only knows the next node, so you can only traverse forward — deleting a node requires a reference to its *previous* node, which is why a dummy head is such a common trick. A doubly linked list adds a `prev` pointer, enabling O(1) backward traversal and O(1) deletion given just the node itself, at the cost of extra memory per node (used heavily in LRU Cache implementations).

Circular linked lists

A circular linked list's tail points back to the head instead of to null. They come up in scheduling/round-robin problems and in Floyd's cycle detection — which is really asking 'does following `next` repeatedly ever loop back on itself?'

Fast & slow pointers

Because you can't jump to 'the middle' of a linked list by index, the standard way to find it is two pointers moving at different speeds — see Two Pointers for the full mechanics. This same fast/slow idea detects cycles (Linked List Cycle) and locates the start of a cycle (Linked List Cycle II).

Reversal

Reversing a linked list — fully or in k-sized groups — means walking the list once while re-pointing each node's `next` to the previous node instead of the next one, tracking three pointers (`prev`, `curr`, `next`) so you don't lose the rest of the list. It's one of the most common 'write it from memory' interview drills because so many other list problems reduce to it.

Merging & splitting

Merging two sorted lists is a direct analogue of the merge step in merge sort: walk both lists with one pointer each, always attaching the smaller head to the result. Merging *k* sorted lists extends this with a min-heap that always holds the current head of each list, so you can pick the global minimum in O(log k) per step instead of O(k).

Dummy head nodes

A dummy (sentinel) node placed before the real head sidesteps special-casing 'what if we need to delete/insert at the very front?' — you operate uniformly on `dummy.next` and return `dummy.next` at the end. It's a small trick that removes a large share of edge-case bugs in list problems.

Stacks & Queues

Two disciplines for ordering work: last-in-first-out and first-in-first-out.

A stack (LIFO — last in, first out) and a queue (FIFO — first in, first out) are both restricted-access lists: you can't reach into the middle, only add/remove from specific ends. That restriction is exactly what makes them useful — they model 'undo history', 'nested structure', and 'process things in the order they arrived' cleanly, and they're the literal mechanism behind recursion (the call stack), DFS (stack-based), and BFS (queue-based).

Stack fundamentals

Push and pop both happen at the same end ('the top') in O(1). Stacks are the natural fit for anything with a nested, 'most recent thing must resolve first' structure: matching parentheses, undo/redo, and simulating recursion iteratively — every recursive function can be rewritten as a loop with an explicit stack.

Queue fundamentals

Enqueue adds to the back, dequeue removes from the front, both O(1) with a proper implementation (a naive array-based queue is O(n) to dequeue from the front — use a deque or two-pointer/circular buffer instead). Queues are what give BFS its level-by-level, 'closest things first' exploration order.

Deques (double-ended queues)

A deque supports O(1) push/pop from *both* ends, so it can act as a stack, a queue, or both at once. This flexibility is exactly what a monotonic deque needs for sliding-window maximum problems.

Monotonic stacks

A monotonic stack keeps its elements in strictly increasing or decreasing order by popping anything that would violate that order before pushing a new element. This is the standard trick for 'next greater/smaller element' style problems — see Monotonic Stack/Queue for the full pattern.

Implementing one with the other

A classic exercise: build a queue from two stacks (push onto one; when you need to dequeue, dump everything into a second stack to reverse the order) or a stack from two queues. It's a good way to internalize *why* the ordering guarantees differ, not just memorize that they do.

Expression evaluation

Stacks are the standard tool for evaluating expressions — Reverse Polish Notation, or full expressions with parentheses and operator precedence (Basic Calculator) — because you need to hold pending operators/operands until you know what they apply to, which is exactly a LIFO problem.

Trees

Hierarchical structure: one root, branching down to leaves, no cycles.

A tree is a connected, acyclic structure with a single root and parent-child relationships — a restricted, hierarchical special case of a Graph. Binary trees (each node has at most two children) and binary search trees (a binary tree with an ordering invariant) are the workhorses; almost every tree problem is really a DFS or BFS traversal wearing a tree-shaped costume.

Traversal orders: preorder, inorder, postorder

These are all depth-first: preorder visits a node before its children (root, left, right — useful for copying/serializing a tree), inorder visits left, root, right (visits BST nodes in sorted order), and postorder visits left, right, root (useful when children must be fully processed before the parent, like computing subtree properties or safely deleting a tree). All three are direct applications of DFS.

Level-order traversal

Visiting a tree level by level (all depth-1 nodes, then all depth-2 nodes, ...) requires a queue instead of the call stack — this is just BFS run on a tree, and it's the standard tool behind Binary Tree Level Order Traversal, zigzag traversal, and right-side-view problems.

Binary Search Trees (BSTs)

In a BST, every node's left subtree contains only smaller values and its right subtree only larger values, which gives O(log n) search/insert/delete *if the tree stays balanced*. Validating this invariant (Validate Binary Search Tree), and exploiting it for the Lowest Common Ancestor of two nodes, are the two most common BST-specific drills.

Balanced trees

An unbalanced BST can degrade to a linked list (O(n) operations) in the worst case — self-balancing trees like AVL trees and Red-Black trees automatically restructure themselves during insert/delete to guarantee O(log n) height. You won't usually implement one from scratch on LeetCode, but 'Balanced Binary Tree' checks the underlying height-balance property directly, and Python's/Java's built-in sorted containers are typically backed by one of these under the hood.

Tree construction

Rebuilding a tree from traversal orders (e.g., preorder + inorder) tests whether you understand what each traversal actually encodes: preorder tells you the root first, and inorder tells you which elements are strictly left vs. right of that root — recursively repeating this reconstructs the whole tree.

Path & subtree problems

A large class of tree problems asks about paths (root-to-leaf, or any node-to-node) or subtree properties (diameter, max path sum, symmetry). These are almost always solved with a postorder DFS that returns information *up* from children to parent, letting the parent combine both children's results in O(1) at each node.

Heaps / Priority Queues

Always know the smallest (or largest) element, instantly.

A heap is a complete binary tree, usually stored in a flat array, that keeps a single invariant: every parent is smaller than its children (min-heap) or larger (max-heap). That invariant gives you O(1) access to the smallest/largest element and O(log n) insert/remove — exactly the operations a priority queue needs, which is why 'heap' and 'priority queue' are used almost interchangeably.

The array representation & heapify

Because a heap is a *complete* binary tree, it can be stored without any pointers at all: for a node at index i, its children live at 2i+1 and 2i+2. 'Heapify' (sift-up on insert, sift-down on removal) restores the heap invariant in O(log n) by swapping a node with its parent or smaller child until it settles into place; building a heap from n elements all at once is O(n), not O(n log n), which surprises most people the first time they see the proof.

Min-heap vs. max-heap

Most languages' standard libraries (Python's `heapq`, Java's `PriorityQueue`) default to a min-heap. To simulate a max-heap in Python, the standard trick is negating values on the way in and out — a small but very commonly needed adjustment.

Top-K problems

'Find the k largest/smallest/most frequent elements' is the single most common heap use case: maintain a heap of size k as you scan the data, popping whenever it exceeds size k, which gives O(n log k) instead of sorting everything at O(n log n). This pairs directly with Hashing when you first need to build a frequency map (Top K Frequent Elements).

The two-heap technique

To track a running median, keep a max-heap for the smaller half of the numbers and a min-heap for the larger half, keeping their sizes balanced within one of each other. The median is then always O(1) to read from the tops of the two heaps — this is the standard solution to Find Median from Data Stream.

Heaps for scheduling & merging

A priority queue naturally models 'always process whichever pending item is most urgent right now' — task scheduling with cooldowns, and merging k sorted linked lists or arrays by always advancing whichever list currently has the smallest head. It's also the workhorse behind Dijkstra's algorithm — see Shortest Path.

Tries

A tree shaped by shared prefixes, built for fast string lookup.

A trie (prefix tree) stores strings by sharing common prefixes along paths from the root — every node represents one character, and a path from the root spells out a prefix. It turns 'does any word start with this prefix?' into an O(L) walk (L = prefix length) instead of scanning every word, which is why it's the backbone of autocomplete, spell-check, and prefix-based search.

Node structure

Each trie node typically holds a fixed-size array or hash map of children (one slot per possible next character) plus a boolean flag marking 'a word ends here.' The flag matters because without it you can't distinguish 'car' from 'card' when both are inserted — you'd only be able to answer prefix questions, not exact-word questions.

Insert & search

Inserting a word walks/creates one node per character and marks the final node as a word-end; searching for a word or a prefix walks the same path and either checks the word-end flag (exact search) or just confirms the path exists (prefix search, `startsWith`). Both are O(L), independent of how many words are stored — the key advantage over storing words in a plain list.

Wildcard / pattern search

Some problems add a wildcard character that can match any letter (Design Add and Search Words Data Structure). This turns a straight-line walk into a small DFS/backtracking search: at a wildcard, branch into every child instead of following one fixed path.

Trie + DFS on a grid

Word Search II combines a trie with a grid DFS: instead of independently searching the grid once per word (slow), you insert all target words into a single trie and walk the grid once, following trie edges — as soon as a path stops matching any trie node, you prune that entire branch.

Beyond strings: bitwise tries

The same prefix-sharing idea works on the binary representations of integers, not just characters — inserting numbers bit-by-bit into a trie lets you find the number that maximizes XOR with a query value in O(32) per query, a neat crossover with Bit Manipulation (Maximum XOR of Two Numbers in an Array).

Graphs

Nodes and edges — the most general structure on this list.

A graph is a set of nodes (vertices) connected by edges, with no restriction to a single root or acyclic shape — Trees and Linked Lists are both just special-case graphs. Almost every technique elsewhere in this guide (DFS, BFS, Union-Find, Topological Sort, Shortest Path, MST) exists specifically to answer some question about a graph — this section is about representing and classifying graphs; the algorithms live in their own sections.

Representations: adjacency list vs. matrix

An adjacency list stores, for each node, a list of its neighbors — O(V + E) space, efficient for sparse graphs, and the default choice in almost all interview problems. An adjacency matrix stores a V×V grid marking which pairs are connected — O(V²) space, but O(1) edge lookup, which matters for dense graphs or when you need to check 'are these two nodes connected?' repeatedly.

Directed vs. undirected

In a directed graph, an edge from A to B doesn't imply an edge from B to A (think: 'course X is a prerequisite for course Y'); in an undirected graph, edges go both ways by definition (think: 'these two people are friends'). Whether a graph is directed changes which algorithms even apply — Topological Sort only makes sense on directed graphs, for instance.

Weighted vs. unweighted

An unweighted graph treats every edge as equally costly, so BFS alone finds shortest paths. A weighted graph assigns a cost to each edge, which is where Dijkstra's, Bellman-Ford, and other Shortest Path algorithms become necessary instead of plain BFS.

Connected components

A connected component is a maximal group of nodes all reachable from each other. Finding them is a repeated DFS/BFS (or a Union-Find sweep over all edges): each time you find an unvisited node, that's a new component, and you flood-fill outward from it to mark everything reachable.

Bipartite graphs

A graph is bipartite if its nodes can be split into two groups such that every edge connects a node in one group to a node in the other — equivalently, if you can 2-color it so no edge connects two same-colored nodes. You check this with a BFS or DFS that alternates colors as it traverses and fails as soon as it finds an edge between two same-colored nodes.

Implicit graphs

Not every graph is handed to you as an edge list — grids (where each cell is a node connected to its neighbors), word-transformation problems (Word Ladder, where an edge exists between two words differing by one letter), and state-space search all define a graph *implicitly* through a 'get neighbors of this state' function. Recognizing that a problem is secretly a graph problem is often the whole insight.

Union-Find (Disjoint Set)

Near-instant answers to 'are these two things connected?'

Union-Find (a.k.a. Disjoint Set Union) maintains a collection of disjoint groups and supports two operations — `union(a, b)` (merge the groups containing a and b) and `find(a)` (which group is a in?) — both nearly O(1) with the right optimizations. It's the tool of choice whenever a problem is really asking about connectivity over a stream of edges, without needing full traversal machinery.

The parent-pointer forest

Each element starts as its own group, pointing to itself as its 'representative.' `union` makes one group's representative point to the other's; `find` walks parent pointers up to the representative, which uniquely identifies the group. Without optimization this degrades toward O(n) per operation in the worst case (a long chain).

Path compression

During `find`, once you've walked up to the representative, re-point every node you passed through directly to that representative. This flattens the tree over time so future `find` calls on those nodes are nearly O(1) — a small change with an outsized effect on performance.

Union by rank / size

When merging two groups, attach the smaller (or shorter) tree under the root of the larger one, rather than picking arbitrarily. This keeps trees shallow on its own, and combined with path compression gives amortized time so close to O(1) per operation that it's described as O(α(n)) — the inverse Ackermann function, which is effectively constant for any input size that could exist.

Cycle detection

For an undirected graph, `union` every edge one at a time — if `find` ever shows both endpoints of an edge are *already* in the same group before you union them, that edge closes a cycle. This is how Redundant Connection is solved in a single pass, and it's the same check Kruskal's MST algorithm uses to skip edges that would create a cycle.

When to reach for it over DFS/BFS

Union-Find shines specifically when edges arrive incrementally (a stream of `union` operations) and you need connectivity answers *between* additions, or when you're processing edges in a specific order (like sorted by weight, for MST). If you just need one-shot 'find all connected components' on a static graph, plain DFS/BFS works just as well and is arguably simpler.

Depth-First Search (DFS)

Go as deep as possible, then backtrack.

Depth-first search explores as far down one path as it can before backtracking to try the next option, typically implemented with recursion (using the call stack) or an explicit stack. It's the default traversal for Trees and Graphs whenever you don't specifically need shortest-path or level-by-level guarantees, and it's the mechanical engine underneath Backtracking.

Recursive vs. iterative DFS

The recursive form is usually the clearest to write — visit a node, then recurse into each unvisited neighbor. The iterative form pushes nodes onto an explicit stack instead, which matters when recursion depth could exceed the language's call-stack limit (very deep or skewed trees/graphs, or languages with small default stack sizes).

DFS on trees

On a Tree, DFS naturally produces preorder, inorder, or postorder traversal depending on when you 'visit' the current node relative to recursing into its children. There's no need to track visited nodes explicitly, since a tree has no cycles by definition.

DFS on graphs

On a Graph, you must track visited nodes explicitly (a set or boolean array), or you'll loop forever around a cycle. This is the algorithm behind connected-component counting, flood fill, and cycle detection in directed graphs (using a 'currently in the recursion stack' marker in addition to 'visited').

DFS on grids

A 2D grid is an implicit graph where each cell connects to its (usually 4, sometimes 8) neighbors. 'Flood fill' style problems — Number of Islands, Max Area of Island, Flood Fill itself — are all grid DFS: start at a cell, recursively visit all connected cells matching some condition, and mark them visited so you don't recount them.

Returning information up the call stack

Many tree/graph problems need each recursive call to *return* something (a height, a sum, a boolean) that the parent combines with its siblings' results — this postorder-style 'compute children first, then combine' pattern is how Diameter of Binary Tree, Subtree of Another Tree, and similar problems are solved in a single DFS pass instead of multiple traversals.

Breadth-First Search (BFS)

Explore level by level — the shortest path in disguise.

Breadth-first search explores a Graph or Tree one full 'ring' of distance at a time, using a queue to process nodes in the order they were discovered. Because it expands outward in strict distance order, plain BFS is the standard way to find shortest paths in an *unweighted* graph — for weighted graphs you need Dijkstra's or Bellman-Ford instead.

The queue-based mechanics

Start by enqueuing the source node (marked visited), then repeatedly dequeue a node, process it, and enqueue any unvisited neighbors (marking them visited *at enqueue time*, not dequeue time — a subtle but important detail to avoid enqueuing the same node multiple times). Every node dequeued is guaranteed to be at the minimum possible distance from the source, which is the entire reason BFS gives shortest paths for free.

Level-by-level processing

To track *which* level (distance) each node is at — needed for level-order tree traversal or 'minimum number of steps' problems — process the queue in batches: capture the current queue size at the start of each round, and dequeue exactly that many nodes before moving to the next level.

Multi-source BFS

When a problem has several valid starting points at once (e.g., 'distance from the nearest 0' in 01 Matrix, or 'time for rot to spread from multiple oranges' in Rotting Oranges), enqueue *all* sources simultaneously before starting. This correctly computes each cell's distance to its nearest source in a single pass, rather than running BFS separately from each source.

BFS on implicit graphs

Just like DFS, BFS often runs on a graph that's never explicitly built — each 'state' (a word, a lock combination, a grid cell) is a node, and a 'get valid next states' function defines the edges on the fly. Word Ladder and Open the Lock are both BFS over an implicit state graph, where the answer is literally 'the BFS distance to the target state.'

BFS vs. DFS: when each wins

Use BFS when you need shortest path / minimum steps in an unweighted graph, or genuinely need level-by-level order. Use DFS when you need to explore full paths (for backtracking, or when *any* path will do), when memory is tight relative to the graph's breadth (DFS's stack can be much smaller than BFS's queue on a wide graph), or when you need postorder-style 'combine children' results.

Backtracking

Try a choice, recurse, then undo it and try the next one.

Backtracking is Recursion with a memory: at each step you make a choice, recurse into the consequences of that choice, and then *undo* it before trying the next choice — systematically exploring every combination while reusing the same state instead of copying it. It's the standard way to generate all permutations, combinations, subsets, and valid configurations under constraints (N-Queens, Sudoku).

The choose–explore–unchoose pattern

Every backtracking function follows the same skeleton: for each candidate choice, add it to the current state, recurse to explore what follows from that choice, then remove it (undo) before moving to the next candidate. That 'unchoose' step is what distinguishes backtracking from plain recursive enumeration — it's how one mutable path/state array can represent every branch of the search tree without allocating a new copy at each node.

Subsets, combinations, and permutations

These three differ only in what's allowed to repeat and whether order matters: subsets pick any group of elements (order doesn't matter, elements aren't reused), combinations are subsets of a fixed size, and permutations use *every* element but in every possible order. All three are solved with near-identical backtracking templates, just with a different loop start index and a different base case.

Pruning

The difference between a backtracking solution that passes and one that times out is almost always pruning — checking a constraint *before* recursing deeper, so you skip entire invalid subtrees instead of discovering the violation only at a leaf. N-Queens and Sudoku Solver are both, at their core, 'brute force with aggressive pruning.'

Backtracking on grids: word search

Word Search combines grid DFS with backtracking's undo step: mark a cell visited while exploring from it, then un-mark it on the way back out, so the same cell can be reused by a different path through the grid later. Forgetting to un-mark is the single most common bug in this pattern.

Backtracking vs. dynamic programming

Both explore a space of choices, but backtracking is for enumerating *all* valid results (or finding whether at least one exists), while Dynamic Programming is for optimizing a single numeric answer over overlapping subproblems. If a problem asks 'list all ways' or 'is it possible', think backtracking; if it asks 'the minimum/maximum/count of ways', check whether overlapping subproblems make DP the faster fit.

Dynamic Programming

Solve each subproblem once, remember the answer, build up.

Dynamic programming solves a problem by breaking it into overlapping subproblems, solving each one exactly once, and reusing those results to build up the final answer — the 'overlapping' part is what separates DP from plain Divide and Conquer, where subproblems don't repeat. If you can write a correct (if slow) recursive solution and notice it's recomputing the same arguments over and over, you've already found a DP problem.

Top-down (memoization) vs. bottom-up (tabulation)

Top-down keeps the natural recursive structure and adds a cache (a hash map or array) keyed by the function's arguments, so repeated calls return instantly. Bottom-up instead builds a table iteratively from the smallest subproblems up to the final answer, avoiding recursion overhead entirely and often making the space optimization (below) easier to see.

Identifying state

The hardest part of DP is usually deciding what a 'state' is — the minimal set of parameters that fully describes a subproblem. Get this wrong (too few parameters) and your recursion isn't actually correct; get it wrong the other way (too many parameters) and your solution is correct but too slow or memory-heavy.

1-D DP

The state is a single index into a sequence — Climbing Stairs, House Robber, and Longest Increasing Subsequence are all 1-D: `dp[i]` depends on some earlier `dp[j]` values. This is the right place to start building DP intuition before moving to multi-dimensional state.

2-D DP: grids, strings, and knapsack

The state is a pair of indices — a position in a grid (Unique Paths), a position in *two* strings simultaneously (Longest Common Subsequence, Edit Distance), or 'how many items considered so far, how much capacity used so far' (the 0/1 knapsack shape, which underlies Partition Equal Subset Sum). Recognizing which of these three shapes a problem matches is most of the battle.

Space optimization

If `dp[i]` only ever depends on the previous row or a small fixed window of previous states, you can discard older rows and keep only what's needed — turning O(n·m) space into O(m) or even O(1). This is a common follow-up question after you've gotten the full-table solution working.

DP on trees and graphs

State doesn't have to be an index — it can be 'the answer for this subtree', combined with children's answers via a postorder DFS (House Robber III is the classic tree-DP intro), or 'the shortest/cheapest way to reach this node' layered on top of Graph traversal. The overlapping-subproblems idea is the same; only the shape of the state changes.

State-machine DP

Some problems (like the multiple variants of Best Time to Buy and Sell Stock) are cleanest modeled as a small state machine — 'holding a stock' vs. 'not holding', with DP tracking the best value achievable in each state at each day. This reframing turns a confusing greedy-looking problem into a mechanical DP transition.

Greedy Algorithms

Make the locally best choice at every step, and trust it stays globally best.

A greedy algorithm builds a solution by always making whatever choice looks best *right now*, never reconsidering it later — no backtracking, no exploring alternatives. It's fast and simple when it works, but it only works when the problem has a specific structure (a 'greedy choice property') that guarantees local optimality leads to a global optimum; proving that structure exists is the real skill.

The exchange argument

The standard way to *prove* a greedy strategy is correct: take any optimal solution that differs from the greedy one, and show you can 'exchange' a piece of it for the greedy choice without making it worse. You rarely need to write this proof formally in an interview, but being able to sketch it in your head is what separates 'I'm guessing this greedy idea works' from actually knowing it does.

Interval scheduling

'Select the maximum number of non-overlapping intervals' is solved by always greedily picking the interval that *finishes earliest* among remaining valid choices — a textbook exchange-argument proof, and the core idea behind Non-overlapping Intervals and Minimum Number of Arrows to Burst Balloons. This overlaps heavily with the Intervals topic, which covers the sorting and sweeping mechanics in more depth.

Jump / reachability games

Problems like Jump Game and Jump Game II are greedy in a different flavor: at each position, track the furthest index reachable so far, and greedily extend it — you never need to consider *which specific* earlier jump got you there, only the best reach available. This 'track the best frontier so far' shape reappears constantly in greedy problems.

Greedy vs. dynamic programming

Greedy and DP both build a solution incrementally, but greedy commits to one choice per step while DP considers all choices and remembers the best. When you're unsure whether a problem is greedy, try to construct a counterexample where the locally best choice leads to a worse global outcome — if you can, it's DP; if you provably can't, it's greedy, and usually much faster.

Common tell: sort first, then sweep

A large share of greedy problems start by sorting the input by some key (start time, end time, ratio, size) and then making a single linear pass, greedily accepting or rejecting each element. Recognizing 'if I sort by X, does the answer become obvious?' is often the fastest way to discover a greedy solution exists at all.

Divide and Conquer

Split, solve independently, combine.

Divide and conquer splits a problem into independent subproblems (usually roughly equal halves), solves each one recursively, and combines their results — the key word being *independent*: unlike Dynamic Programming, the subproblems don't overlap, so there's nothing to memoize. Merge sort and quick sort are the canonical examples, and they're worth re-deriving from this lens once you already know how they work mechanically.

The three-step template

Divide: split the input into smaller pieces. Conquer: solve each piece recursively (down to a trivial base case). Combine: merge the sub-results into a solution for the original problem. The combine step is usually where the real cleverness lives — merge sort's combine step (merging two sorted halves) is doing all the actual sorting work.

The Master Theorem

For a recurrence of the form T(n) = a·T(n/b) + f(n) (a subproblems, each of size n/b, plus f(n) work to combine), the Master Theorem gives a direct formula for the overall time complexity by comparing f(n) against n^(log_b a) — it's how you can immediately know merge sort is O(n log n) without re-deriving it from a recursion tree every time.

Counting via divide and conquer

Beyond sorting, D&C shows up whenever 'combine' can count *cross-pairs* between two halves in less than brute-force time — Count of Smaller Numbers After Self and Reverse Pairs both piggyback on merge sort's merge step, counting inversions between the left and right halves as they're merged, for an O(n log n) solution to what looks like an O(n²) counting problem.

Fast exponentiation

Computing x^n naively takes n multiplications; divide and conquer computes it in O(log n) by noting x^n = (x^(n/2))², recursively halving the exponent at each step. This 'repeated squaring' idea generalizes well beyond Pow(x, n) — it's the same trick behind fast matrix exponentiation for certain DP speedups.

D&C vs. plain recursion vs. DP

Every divide-and-conquer algorithm is recursion, but not every recursive algorithm divides into *independent* halves — Backtracking recurses to explore choices, and DP recurses into *overlapping* subproblems that benefit from caching. If subproblems don't overlap, there's nothing to memoize, and you're firmly in divide-and-conquer territory instead.

Topological Sort

Ordering tasks so every prerequisite comes before what depends on it.

A topological sort orders the nodes of a directed acyclic graph (DAG) so that every edge u→v places u before v — in plain terms, 'a valid order to do these tasks given their prerequisites.' It only exists if the graph has no cycles, so most topological-sort problems are secretly cycle-detection problems wearing an ordering costume.

Kahn's algorithm (BFS-based)

Compute the in-degree (number of incoming edges) of every node, then repeatedly remove nodes with in-degree 0 (they have no unmet prerequisites), decrementing the in-degree of their neighbors as they're removed — this is a direct application of BFS with a queue seeded by all initially-zero-in-degree nodes. If you can't remove all n nodes this way, the graph has a cycle and no valid ordering exists.

DFS-based topological sort

Run DFS from every unvisited node, and each time a node finishes exploring *all* of its descendants, push it onto the front of a result list (or append and reverse at the end). This works because a node can only finish after everything it depends on has already finished — cycle detection here means tracking nodes currently 'in progress' on the recursion stack, not just visited overall.

Course-scheduling problems

Course Schedule (does a valid order exist?) and Course Schedule II (produce that order) are the direct textbook applications — 'course B requires course A' is exactly an edge A→B, and the question is whether the prerequisite graph is a DAG.

Alien Dictionary: extracting a graph from constraints

Not every topological-sort problem hands you a graph directly — Alien Dictionary derives edges by comparing adjacent words in a sorted word list (the first differing letter between two adjacent words tells you one letter must come before another), then topologically sorts the *letters*. Recognizing that ordering constraints imply a graph is the core insight.

Beyond a single valid order

Some problems ask for more than just *a* valid order: Minimum Height Trees asks which node(s) minimize the tree's height (solved by repeatedly peeling off leaves — a close cousin of Kahn's algorithm), and Sort Items by Groups Respecting Dependencies layers a second level of topological sort on top of the first (groups, then items within groups).

Shortest Path

Cheapest way from A to B, once edges have different costs.

Plain BFS finds shortest paths only when every edge costs the same. As soon as edges have different weights, you need an algorithm that accounts for cost, not just hop count — which one depends on whether weights can be negative and whether you need one source or all pairs.

Dijkstra's algorithm

Dijkstra's greedily expands the closest unvisited node first, using a min-heap keyed by current best-known distance, and relaxes (updates) neighbor distances whenever a shorter path is found through the node just popped. It's correct only when all edge weights are non-negative — a negative edge could make a 'later' path cheaper after Dijkstra has already committed to a node as final, breaking the greedy guarantee.

Bellman-Ford

Bellman-Ford relaxes *every* edge, V-1 times, which is slower (O(V·E)) than Dijkstra but correctly handles negative edge weights and can explicitly detect negative cycles (if an edge can still be relaxed after V-1 rounds, a negative cycle exists). Cheapest Flights Within K Stops is a bounded version of this idea — Bellman-Ford relaxation, capped at K rounds instead of running to convergence.

Floyd-Warshall

When you need shortest paths between *all pairs* of nodes rather than from one source, Floyd-Warshall's O(V³) dynamic-programming approach (try every node as a possible 'via' point, for every pair) beats running Dijkstra from every node individually on dense graphs, and it also handles negative weights (though not negative cycles).

0-1 BFS

When every edge weight is either 0 or 1, you don't need a full priority queue — a deque suffices: push 0-weight edges to the *front* and 1-weight edges to the *back*, which keeps the deque implicitly sorted by distance. This gives Dijkstra's correctness at plain BFS's O(V + E) speed for this special but common case.

Shortest path via binary search

Some 'shortest path' problems are really 'does a path exist using only edges ≤ x?' wrapped in a search over x — binary search on the answer, paired with a BFS/DFS feasibility check at each candidate x. Path With Minimum Effort and Swim in Rising Water both use this combination instead of a pure shortest-path algorithm.

Minimum Spanning Tree (MST)

Connect every node as cheaply as possible, with no cycles.

A minimum spanning tree connects all nodes of a weighted, undirected graph using the minimum possible total edge weight, with exactly V-1 edges and no cycles. It answers 'what's the cheapest way to make sure everything is connected' — infrastructure/network-cost problems in disguise.

Kruskal's algorithm

Sort all edges by weight ascending, then greedily add each edge unless it would create a cycle — checked in O(α(n)) via Union-Find, which is precisely why Union-Find and MST are taught together. This is a greedy algorithm whose correctness relies on the 'cut property': the cheapest edge crossing any cut of the graph is always safe to include.

Prim's algorithm

Prim's grows a single tree outward from an arbitrary start node, at each step greedily adding the cheapest edge that connects the current tree to a new node — implemented efficiently with a min-heap of candidate edges, very similar in shape to Dijkstra's algorithm (the difference: Dijkstra tracks distance-from-source, Prim's tracks distance-from-tree).

Kruskal's vs. Prim's

Kruskal's is usually simpler to implement and preferred for sparse graphs (it processes edges globally, sorted once); Prim's with a heap is preferred for dense graphs where the number of edges is much larger than the number of nodes. Both always produce a minimum-weight spanning tree, though not necessarily the *same* tree when weights tie.

Why MST is rare in pure form on LeetCode

True 'compute the MST' problems are less common on LeetCode than the algorithms *inspired by* MST logic — Min Cost to Connect All Points is close to textbook Prim's/Kruskal's, while others (Number of Operations to Make Network Connected) really just need the *count* of redundant edges via Union-Find, without fully constructing the tree.

Variants: second-best MST, critical/pseudo-critical edges

Some problems go a level deeper — Find Critical and Pseudo-Critical Edges in Minimum Spanning Tree asks which edges *must* be in every MST (critical) versus which *could* be in some MST (pseudo-critical), solved by re-running Kruskal's with each edge forcibly included or excluded and comparing total weights.

Bit Manipulation

Working at the level of individual bits for constant-factor speed and clever tricks.

Bit manipulation operates directly on the binary representation of numbers using AND, OR, XOR, NOT, and shifts. It rarely changes an algorithm's asymptotic complexity, but it enables O(1) tricks for problems that otherwise look like they need extra space, and it's the foundation of bitmask techniques used across DP and Backtracking.

The core operators

AND (`&`) is true only when both bits are 1 (used for masking/checking specific bits), OR (`|`) is true when either bit is 1 (used for setting bits), XOR (`^`) is true when the bits differ (used for toggling bits and for its 'cancels itself out' property: x ^ x = 0), and NOT (`~`) flips every bit. Left shift (`<<`) multiplies by a power of two; right shift (`>>`) divides by one, with care needed around sign bits for negative numbers.

XOR's cancellation property

Because x ^ x = 0 and x ^ 0 = x, XOR-ing every element of a list together cancels out any value that appears an even number of times, leaving only the value that appears an odd number of times. This single property solves Single Number in O(n) time and O(1) space, with no hash map needed at all.

Counting and manipulating individual bits

`n & (n-1)` clears the lowest set bit — repeating this until n becomes 0 counts the total number of set bits (Number of 1 Bits), and it's the key relation behind the O(n) DP solution to Counting Bits (`bits[n] = bits[n & (n-1)] + 1`). `n & (-n)` isolates the lowest set bit on its own, useful for Fenwick tree indexing (see Segment/Fenwick Trees).

Bitmasks for subsets

Any subset of an n-element set can be represented as an n-bit integer, where bit i is 1 if element i is included — looping `mask` from 0 to 2^n - 1 enumerates every subset, which is a common alternative to explicit backtracking for small n, and the standard state representation for 'traveling salesman'-style DP (bitmask DP).

Sign, overflow, and two's complement

Most languages represent negative integers using two's complement, where the leftmost bit signals sign — this is why right-shifting a negative number can behave unexpectedly (arithmetic vs. logical shift) and why problems like Sum of Two Integers (implement addition using only bitwise operators) hinge on correctly handling carry bits and overflow at the word-size boundary.

Math & Number Theory

The arithmetic facts that keep showing up underneath other topics.

A small toolkit of number-theory facts — GCD/LCM, primality, modular arithmetic, and basic combinatorics — resurfaces constantly as a supporting piece inside problems that are 'really' about something else. It's rarely the whole problem, but not knowing it turns an easy problem into a stuck one.

GCD, LCM, and the Euclidean algorithm

The greatest common divisor of two numbers can be computed in O(log(min(a,b))) via the Euclidean algorithm: gcd(a, b) = gcd(b, a mod b), repeated until the remainder is 0. The least common multiple follows directly from it: lcm(a, b) = a·b / gcd(a, b) — this pair shows up any time a problem involves fractions, ratios, or 'smallest number divisible by both.'

Primality & the Sieve of Eratosthenes

Checking whether a single number is prime takes O(√n) by testing divisibility up to its square root. When you need *all* primes up to n, the Sieve of Eratosthenes does it in O(n log log n) by marking multiples of each prime as composite, which is dramatically faster than checking each number individually (Count Primes).

Modular arithmetic

When an answer can be astronomically large, problems ask for it 'modulo 10^9 + 7' — a large prime chosen so that intermediate arithmetic (especially multiplication in DP/combinatorics problems) doesn't overflow standard integer types, while addition and multiplication still distribute correctly under the modulus (`(a·b) mod m = ((a mod m)·(b mod m)) mod m`).

Basic combinatorics

Counting problems often reduce to permutations (n! / (n-k)!, order matters) or combinations (n! / (k!(n-k)!), order doesn't) — recognizing which one a problem is describing in words ('how many ways to arrange' vs. 'how many ways to choose') is usually more of the difficulty than the formula itself.

Digit manipulation & base conversion

Problems that talk about digits directly (reversing a number, checking a palindrome numerically, Roman numeral conversion) are usually solved with repeated `% 10` (extract the last digit) and `// 10` (drop it) rather than converting to a string, which keeps them O(1) extra space and sidesteps string-parsing edge cases.

Segment Trees & Fenwick Trees

Range queries and point updates, both in O(log n), without recomputing from scratch.

When you need to repeatedly query a range (sum, min, max) of an array *and* update individual elements, a plain array forces a tradeoff: prefix sums give O(1) range queries but O(n) updates, while recomputing per query gives O(1) updates but O(n) queries. Segment trees and Fenwick trees (Binary Indexed Trees) break that tradeoff, giving O(log n) for both.

Segment trees: structure

A segment tree is a binary tree where each node represents a range of the array, the root represents the whole array, and each node's two children split its range in half — leaves represent single elements. Any range query decomposes into O(log n) of these precomputed node-ranges instead of scanning every element.

Range queries & point updates

Querying a range means descending the tree and combining results only from nodes whose range falls fully inside the query range (O(log n) such nodes). Updating a single element means updating its leaf and then re-combining values up the O(log n) path to the root — both operations touch only a logarithmic slice of the tree.

Lazy propagation

When updates apply to a whole *range* at once (not just a single element), eagerly updating every affected leaf would be O(n) per update. Lazy propagation defers those updates — marking a node 'pending' and only pushing the update down to children when that subtree is actually visited by a later query — restoring O(log n) per range update.

Fenwick trees (Binary Indexed Trees)

A Fenwick tree achieves the same O(log n) point-update / prefix-query bounds as a segment tree but with a much smaller, cleverer implementation: a single array where each index is responsible for a range determined by its lowest set bit (`i & (-i)`, straight out of Bit Manipulation). It's simpler to code and uses less memory, but it's naturally suited to prefix-sum-style queries — segment trees generalize more easily to arbitrary range operations (min, max, gcd).

When to reach for one

If a problem's array is static (no updates), plain prefix sums are simpler and sufficient — don't reach for these structures unnecessarily. Reach for a Fenwick tree or segment tree specifically when updates and range queries are *interleaved* (Range Sum Query - Mutable is the textbook signal), or when you need range statistics that plain prefix sums can't give you, like counting inversions (Count of Smaller Numbers After Self, solvable either this way or via Divide and Conquer).

Monotonic Stack / Queue

Keep only the candidates that could still matter, in sorted order, for free.

A monotonic stack (or deque) maintains its elements in strictly increasing or decreasing order by popping anything that would violate that order *before* pushing a new element. It turns a class of problems that look like they need O(n²) comparisons — 'find the next greater element for every position' — into a single O(n) pass, because each element is pushed and popped at most once.

Why popping is safe

When a new, larger element arrives and you're maintaining a decreasing stack, every smaller element currently on top of the stack can *never* be the answer for anything after this point — the new element is both closer and larger, so it dominates them. That domination argument, not just the mechanics of pushing/popping, is what actually proves the technique correct, and it's worth being able to restate for any monotonic-stack problem you solve.

Next greater / smaller element

Walk the array once, maintaining a stack of indices whose 'next greater element' hasn't been found yet. When the current element is larger than the stack's top, pop it and record the current element as its answer — repeat until the stack top is larger again (or empty), then push the current index. Next Greater Element I/II and Daily Temperatures are the direct template for this.

Largest rectangle in histogram

This one uses a monotonic *increasing* stack of bar indices: when a shorter bar arrives, it means every taller bar on the stack can't extend any further right, so you pop them one at a time and compute the rectangle each could have formed, using the stack (after popping) to know how far left it could have extended. It's the same 'pop and resolve' shape as next-greater-element, just computing an area instead of a partner index.

Monotonic deque for sliding-window max

For Sliding Window Maximum, a plain monotonic stack isn't enough because elements also need to expire once they fall outside the window on the *left* — a deque solves this by popping smaller elements from the back (same domination argument as above) while also popping expired indices from the front. The front of the deque is always the current window's maximum, in O(1).

Recognizing the pattern

The phrase to watch for is 'next/previous greater or smaller element', or any problem where the answer for each element depends on the *closest* qualifying neighbor in one direction. If a problem instead needs the closest neighbor by *position* rather than by value ordering, Two Pointers or plain iteration is usually a better fit than a monotonic stack.

Intervals

Ranges that start and end — sort them, then sweep.

Interval problems deal with ranges defined by a start and end (meetings, bookings, line segments) and almost always follow the same recipe: sort by start (or end) time, then sweep through in a single pass, merging, counting overlaps, or making a greedy choice as you go. Once you see the sort-then-sweep shape, most interval problems become a matter of getting the merge/overlap condition exactly right.

Merging overlapping intervals

Sort intervals by start time, then walk through them keeping a 'current merged interval': if the next interval's start is ≤ the current merged interval's end, extend the merge; otherwise, close out the current interval and start a new one. This single pattern solves Merge Intervals and underlies almost every other problem in this section.

Inserting into a sorted set of intervals

Insert Interval is the same merging idea run in three phases in one pass: copy every interval that ends before the new one starts untouched, merge every interval that overlaps the new one into it, then copy every interval that starts after the new one (now merged) ends. No need to re-sort — the input is already sorted, so a single linear scan suffices.

Detecting & counting overlaps

Meeting Rooms asks 'can all these meetings happen with no overlap at all?' (sort by start, check each against the previous end); Meeting Rooms II asks 'what's the *maximum* number happening at once?', solved either by a min-heap of end times (pop whenever the next meeting starts after the earliest-ending one finishes) or by separately sorting start times and end times and sweeping both with two pointers.

Interval scheduling as greedy

'Select the maximum number of non-overlapping intervals' — Non-overlapping Intervals, Minimum Number of Arrows to Burst Balloons — is solved by sorting by *end* time and greedily keeping every interval that doesn't conflict with the last one kept. See Greedy for why sorting by end time (not start time) is the detail that makes this provably optimal.

Sweep-line & interval intersections

Interval List Intersections walks two already-sorted interval lists with two pointers simultaneously, computing the overlap of the current pair and advancing whichever interval ends first — a two-list variant of the same sweep idea. Employee Free Time takes this further: merge every employee's intervals together, then the *gaps* between merged intervals are the shared free time.
